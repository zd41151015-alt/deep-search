# Repository Guidance

## Scope

- This repository implements the domain-specific Startup Opportunity Research Harness described in `startup-opportunity-codex-research-harness.md`.
- `startup-opportunity-implementation-progress.md` is the historical construction ledger. Consult it only when tracing implementation history or accepted verification evidence; its former Gate, controller, and `READY` slice state does not gate maintenance, bug fixes, or later product iteration.
- Keep the implementation on the frozen TypeScript 7.0.2 / Node.js 24.18 / npm 11.16 stack. Do not add another package manager, lockfile, or implementation language.
- The deterministic Harness must not make hidden LLM calls or reimplement Codex's agent loop, permissions, or thread lifecycle.

## Research Contracts

- Formal research enters through `$startup-opportunity` or a compatible invocation of that Skill. The Skill is a Runtime entry, not an authority for repository architecture or contract version strategy.
- `$startup-opportunity` is a business Skill for executing Startup Opportunity research Runs. Do not invoke or follow it as a workflow for repository exploration, debugging, coding, refactoring, schema design, code review, test strategy, or engineering task delegation. Coding agents must use this `AGENTS.md`, the owning production modules and current contracts, and the applicable engineering documentation as implementation authorities. Reading the Skill is not prohibited: inspect the relevant parts when needed to understand or verify an affected end-to-end Runtime workflow, especially its entry behavior, public instructions, command sequence, Agent or Lane responsibilities, reachable workflow, or user-visible outputs. In that inspection it remains a Runtime consumer/orchestration and documentation surface, not an authority for architecture, schemas, policies, implementation design, or tests. If it conflicts with an owning current contract or production module, resolve the engineering truth from those authorities and update the Skill atomically when its public Runtime surface is in scope.
- Runtime support is current-only. `harness/schemas/current.json` is the single editable schema manifest; it has no base manifest, release number, or historical bundle selection role.
- Do not add adapters, fallbacks, migrations, old-Run detection protocols, or fixtures solely to keep retired Run bytes readable. After a code or contract update, use a new `run_id`; an old Run may fail ordinary current Manifest/schema validation and is not recovered, continued, or revalidated.
- Ordinary fixes update the current manifest, producers, consumers, validators, policies, and current fixtures atomically. Keep a numbered domain contract only while a current producer or consumer reaches its distinct business shape; do not use numbering as a Store compatibility mechanism.
- Current-only support does not weaken recovery inside one current Run: immutable revisions and refs/hashes, atomic Manifest publication, exact receipt replay, checkpoint/reopen, and crash recovery remain mandatory.
- Chat messages and subagent completion summaries are not formal artifacts.
- Never fabricate evidence references, URLs, user quotes, market data, or successful external validation.
- A subagent writes only its assigned output path and Evidence Store operations; it must not edit another lane's output, the current plan, manifest, comparison policy, decision brief, or report.
- Persist user scope or candidate corrections through the G0.3 `decisions.jsonl` append contract.
- Runtime plan changes must follow Gap Snapshot -> Adaptation Decision -> policy validation -> immutable Plan Revision. Never overwrite the current plan directly.
- Do not execute or track interviews, landing pages, deposits, advertising, paid experiments, MVP tests, or other external validation actions.
- When report outputs exist, `report.json`, `decision-brief.md`, and `report.md` must pass schema, traceability, freshness, and consistency checks before delivery.

## Research Non-Degradation

- Every implementation, contract, schema, validator, Gate, Store, Runtime, reporting, tooling, and review change must explicitly assess whether it weakens the research process, information breadth, semantic fidelity, supported workflow, conclusion quality, or user-visible report. A mechanically stricter or more deterministic implementation is not acceptable if it makes legitimate research less expressive, less complete, or unreachable.
- Preserve first, weight later. News, reviews, forums, vendor material, regulatory material, APIs, datasets, proxies, estimates, supporting Evidence, opposing Evidence, background material, and contradictory material remain eligible research inputs when lawfully accessible. Use provenance, source/evidence roles, freshness, limitations, confidence, and conclusion ceilings to constrain what they support; do not remove them or introduce provider/source/API allowlists merely because they are weak or non-canonical.
- Preserve distinct research states. `partial`, `unavailable`, `unknown`, `inferred`, `not_applicable`, and `no_evidence_found` are not interchangeable. Do not turn incomplete, weak, indirect, conflicting, or currently unusable Evidence into an assertion that no Evidence exists.
- If the current Artifact or workflow cannot faithfully express a legitimate research result, update the current contract, producer, consumer, validator, report projection, and tests atomically. Do not compensate for an expressiveness gap by rejecting the result, forcing an inaccurate value, fabricating completeness, or requiring the Agent to author Harness-owned mechanical fields.
- Integrity controls may fail closed for authenticity, security, access control, exact ref/hash and same-Run ownership, immutable publication/recovery, or conclusions that exceed their formal Evidence ceiling. Do not broaden failure conditions for mechanical convenience. Existing domain policies may limit confidence, ranking, or recommendations when Evidence is weak, but the underlying material and its honest disposition must remain visible and traceable.
- Engineering changes must not make a supported research action, current workflow, honest terminal outcome, recovery path, or required report unreachable. Additional structured input is justified only when it captures research meaning that cannot be derived mechanically and has a demonstrated positive effect on research or user-visible truthfulness.
- Every code review must treat research non-degradation as an independent acceptance dimension, not as an incidental side effect of schema or test correctness. Apply the implementation/review checklist in `docs/current-contract-maintenance.md` and require focused positive and negative regressions for affected observable behavior.
- Every delegated engineering task must state both boundaries explicitly: research behavior must not be degraded, and `$startup-opportunity` must not be invoked or followed as coding-agent guidance. Delegation must not turn that restriction into a blanket ban on reading: when end-to-end Runtime behavior may be affected, the task must inspect the relevant Skill surface as a consumer/orchestration contract and verify consistency without treating its workflow text as implementation authority. A delegated task may update or test the Skill only when that public Runtime surface is in scope.

## Development

- Do not use keywords, substrings, regular-expression hits, token counts, or other lexical matching over free-form prose as authority for research semantics, Artifact classification, Evidence disposition, workflow selection, state transitions, Gate outcomes, ranking, confidence, recommendation ceilings, publication eligibility, report omission, or any other domain behavior. Represent and validate those meanings through owning structured fields, enums, typed refs/hashes, provenance, and current contracts. Lexical checks are allowed only when the property being checked is itself explicitly lexical (for example, schema syntax, path shape, secret detection, or a contract-defined user-visible literal boundary); they must remain non-semantic, scope- and position-aware, avoid converting incidental wording into domain truth, and include positive and negative regressions for legitimate literal occurrences. Code review must reject prose-keyword-driven behavior unless the owning contract explicitly establishes such a lexical boundary.
- Use Node.js `24.18.x` and npm `11.16.x`; install exactly from `package-lock.json` with `npm ci`.
- Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run validate:schemas`, `npm run validate:current-contract`, and `npm run verify:skeleton` for repository/toolchain/schema changes. The full `npm test` entry covers every test file in `validate:fixtures`; keep `validate:fixtures` as a focused development command instead of repeating it after `npm test`.
- Add production behavior only in the domain module that owns it. A directory, empty schema, mock-only path, or deferred-command entry is not evidence that downstream behavior is implemented.
- Keep generated output under ignored paths such as `dist/`; do not commit research raw data or secrets.
- Treat `manifest.json` as the atomically replaced current index; publish formal envelopes and checkpoints immutably, and recover only from validated on-disk state.
